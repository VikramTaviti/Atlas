# ATLAS threat model

## Scope and assets

This model covers implemented plan-input/compiler, local execution-backend, Milestone 3 tool-gateway, Milestone 4 event/artifact/replay, and Milestone 8 HTTP admission boundaries. Assets include source workspaces, credentials, operator policy, plan/config provenance, tool outputs, evaluation integrity, and audit evidence. Trust boundaries exist between task/provider content and Atlas, planner proposals and the compiler, HTTP callers and the API, runtime and tools, workspace and host, persistent local artifacts and process memory, and candidate experiments and baseline evaluation.

## Adversaries and untrusted inputs

Assume a malicious or compromised user task, repository file, web page, agent/model output, tool response, plan JSON, dependency, or optimizer proposal. A legitimate user may also accidentally submit a malformed or resource-amplifying graph. No model or tool output is trusted because it is syntactically valid.

## Threats and planned controls

| Threat | Impact | Required controls | Current status |
|---|---|---|---|
| Prompt injection in task/repository/tool content | Agent acts outside intended task | Treat retrieved content as data; gateway-enforced authorization; isolate instructions from data where supported | Central gateway requires operator and profile allowlists; prompt-injection defenses remain model/provider responsibilities |
| Unknown node/tool/agent reference | Confused deputy or unintended capability | Closed node-kind enum; trusted registry resolution; deny unknown references | Node kinds and refs checked; ReAct tool calls must also match the agent profile allowlist |
| Agent attempts unauthorized or excessive tool use | Data access or tool abuse | Agent-specific tool allowlists; typed schemas; per-turn/per-agent call ceilings; deny invalid calls | ReAct limits plus gateway operator allowlist, capabilities, schemas, per-run calls, concurrency, timeout and byte budgets |
| Malicious graph cycles, excessive size/depth/fan-out | CPU/memory exhaustion or stalled execution | Deterministic DAG validation and hard graph/depth/parallelism limits | Implemented structural controls; tests included |
| Invalid/ambiguous schema | Contract bypass or downstream crash | Validate JSON Schema at model boundary; reject unknown model fields | Implemented for model/tool schemas and node output schema |
| Path traversal/workspace escape | Unauthorized file access or modification | Canonical path containment checks in gateway; scoped mounts; no direct host access | Gateway resolves paths, blocks traversal and symlink escape; read tool independently contains paths |
| Command injection/malicious dependencies | Host compromise or data theft | No arbitrary host shell; disposable isolated container, resource limits, command allowlist | Docker runner uses exact configured argv, no network, read-only workspace/root, dropped capabilities and resource bounds; Docker/daemon isolation remains host-dependent |
| Secret exfiltration via outputs/logs/artifacts | Credential compromise | Secret manager, scoped credentials, redaction, output filtering, retention controls | JSON logs and ReAct traces redact secret-like keys, bearer strings, assignments and configured literals; audit stores hashes only; semantic/encoded secrets and future artifacts need separate controls |
| Retry storms/duplicate side effects | Cost, corruption, duplicate external actions | Bounded retries, idempotency keys, per-run budgets, approval for side effects | Retry limits and idempotent retry guard; gateway per-run budget; side-effect/destructive tools require action-bound, expiring approval; idempotency keys remain future work |
| Optimizer privilege escalation/evaluator manipulation | Unsafe config promotion | Typed allowlisted diffs; immutable policies/evaluators; paired isolated experiments; human approval | Strict patch schema rejects policy fields; skills/tools/tokens are bounded; paired gates and explicit hash-bound promotion are implemented; authenticated human identity remains an external integration |
| Benchmark leakage/contamination | False improvement claims | Versioned cases, isolation, fixed evaluators, provenance and multiple trials | Suite versions/cases and per-case reports persist with evaluator/environment IDs; fixture benchmark is labeled illustrative; real dataset isolation is owned by application runner |
| Candidate contaminates baseline or benchmark environment | Invalid comparison or unsafe artifact mutation | Isolated workspaces and equal controls per candidate | Evaluation runner contract receives same case/environment; ATLAS core does not itself provision isolated workspaces, so real runners must supply isolation |
| Spoofed/stale approval | Unauthorized consequential action | Authenticated approver identity, action-bound expiring approvals, one-time use | Gateway verifies request ID, exact input hash, nonempty approver ID, and expiry; production identity authentication/provider and durable replay-resistant approval service remain deployment responsibilities |
| Artifact disclosure or tampering | Sensitive inputs/results exposed or replay evidence changed | Access controls, encryption, digest verification, retention policy | Local artifacts use owner-only file permissions and SHA-256 verification; at-rest encryption, retention/deletion service and host-admin tamper resistance are not included |
| Replay divergence or accidental side effects | False reproduction or external effects repeated | Recorded tool outputs by default; explicit mode and divergence report | Backend replay never calls tool adapters, matches exchanges by node/tool order, flags changed input hashes and output divergence; agent adapters are re-executed and marked nondeterministic |
| Untrusted HTTP caller submits a plan referencing privileged tools | API becomes a confused deputy | Authenticate requests; compile against a server-owned registry; enforce gateway policy on every call; never accept tool code or policy in request bodies | API accepts typed plans only, resolves refs against startup-configured registries, and uses the existing deny-by-default gateway. Authentication is injectable but disabled by default; deployment must provide real identity and authorization. |
| API run flood or cancellation race | Process exhaustion or work continues after cancellation | Bound admission/concurrency; request limits and per-principal quotas; cancellation propagation; durable queue/leases for multi-worker operation | In-process concurrency and total admitted run count are bounded; cancellation propagates to the run task. Request size/rate quotas and multi-worker durable admission are not implemented. |
| Provider credential leakage | Unauthorized model usage or billing/quota abuse | Secret manager/environment injection; never serialize credentials; sanitize provider failures; redact logs/traces | Gemini key is read from environment or a secret file, omitted from telemetry and genericized on provider errors. Local `.env`/`secrets/` are ignored by Git and Docker build context. |

## Current controls and limitations

The compiler parses strict immutable Pydantic models and cannot carry operator policy fields. A per-run gateway mediates both DAG and ReAct calls, with deny-by-default operator and profile allowlists, schema/capability checks, budgets, workspace containment, approvals and SQLite audit. Milestone 4 adds correlated local run/node/tool event records, content-addressed artifact references, OpenTelemetry API spans, event inspection, and tool-output replay. Milestones 5–6 add versioned evaluation reports, a patch schema that cannot express policy mutations, hard promotion gates, persistent evidence, hash-bound approval, and versioned rollback. Milestone 8 adds typed HTTP run admission, but authentication is disabled by default and request quotas are not implemented. Milestone 9 reads Gemini keys from environment/secret-file configuration and emits generic provider errors; operators remain responsible for protecting env values, secret files, and persisted prompts/tool observations. Plans resolve only against server-configured registries and every tool still passes through the gateway. Artifacts may contain raw sensitive values to permit exact tool playback; local owner-only permissions are not encryption. The local audit/event/evaluation/harness stores are not tamper-proof against filesystem/host administrators and are not distributed. Evaluation runner isolation and approval identity authentication remain application responsibilities. Fixture benchmark values are illustrative. Docker runner safety depends on correct daemon configuration and operator-provisioned trusted image. Traces redact configured/pattern-detectable secrets, but arbitrary encodings or semantic secrets can evade redaction. A stable hash is integrity identification only, not a signature.

## Security requirements before broader tool integration

- Use the implemented single execution-time gateway for all new tool adapters; maintain deny by default.
- Preserve schema validation, filesystem/network scope, and isolated command execution.
- Apply operator ceilings independently of plan proposals. Token/cost-specific budgets remain future work.
- Preserve append-only audit decisions and outcome recording.
- Configure artifact access, encryption, redaction, and retention before storing sensitive production workloads.
- Require explicit, authenticated approval for high-impact side effects and harness promotion.
- Test attack cases including traversal, injection, privilege escalation, cancellation, and duplicate retries.
